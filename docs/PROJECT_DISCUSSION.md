# AI 사내 업무 안내 서비스 프로젝트 대화 정리

- 정리일은 2026년 11월 5일이다.
- 프로젝트의 목표, 대화 중 결정한 범위, 제안된 진행 방식과 가상 업무 자료 초안을 정리했다.
- 가상 회사 문서는 팀 검토용 초안이다. 문서 안의 승인 상태와 사건은 교육·검증을 위한 가상 설정이다.

## 1. 프로젝트 소개

> 임직원이 사내 문서를 바탕으로 과거 처리 사례와 현재 적용되는 기준을 구분하고, 다음 절차와 담당자를 확인할 수 있는 AI 업무 안내 서비스.

초기 아이디어는 신입사원을 위한 온보딩 교육 프로그램이었다. 대화를 통해 업무에 필요한 맥락과 자료를 찾고, 과거 사례와 현재 기준의 차이를 설명하는 서비스로 구체화했다.

첫 검증은 가상 의류 쇼핑몰 개발팀을 대상으로 진행한다. 배포 시점에는 산업과 직무에 관계없이 각 조직의 자료를 활용할 수 있는 범용 서비스를 목표로 한다.

## 2. 팀 구성과 프로젝트 목표

### 2.1 처음 정한 역할

| 구성원 | 담당 영역 |
|---|---|
| 사용자 | PM, 백엔드, AI, 인프라 |
| 팀원 1 | 프론트엔드 |
| 팀원 2 | AI |

사용자는 CS와 개발 지식이 없는 상태를 기준으로 설명받고, 실제 업무에 가까운 프로젝트 과정을 천천히 배우며 진행하기를 원한다.

### 2.2 사용자가 밝힌 완료 목표

> 실제 신입사원이 사용할 수 있는 서비스를 배포하고, 세 명 모두 기획부터 개발, 배포, 오류 해결까지 왜 그렇게 했는지 설명할 수 있으면 좋겠다. 취업 포트폴리오로도 활용하고 싶다.

| 목표 | 남길 증거 |
|---|---|
| 실제 사용 | 사용자 피드백과 그에 따른 개선 기록 |
| 팀 전체의 이해 | 기술 선택 이유, 동료 검토, 서로의 영역을 설명하는 시연 |
| 취업 포트폴리오 | 해결한 문제, 개인 기여, 오류 원인과 해결, 개선 전후 결과 |

기능마다 필요한 이유, 선택한 방식의 이유, 결과를 확인한 방법을 기록하는 진행 방식을 제안했다.

### 2.3 협업 보완 제안

PM·백엔드·AI·인프라가 한 사람에게 집중되므로, 주 담당자를 유지하면서 다른 팀원이 결과를 확인하는 방식을 제안했다. 아래는 추가 제안이며 팀에서 확정한 역할 재배분은 아니다.

| 구성원 | 함께 맡으면 좋은 일 |
|---|---|
| 사용자 | 우선순위 정리, 기술 선택 이유와 서버 동작 설명 |
| 팀원 1 | 사용성 확인, 화면에서 서버까지 통합 확인 |
| 팀원 2 | 교육 자료 정리, 평가 사례 작성, AI 연동 검토 |

세 사람 모두 프로젝트를 실행하고 다른 사람의 변경 내용을 읽을 수 있는 상태를 지향한다. 담당자가 구현한 내용을 다른 팀원이 설명해 보는 시간을 두는 것도 제안했다.

## 3. 문제를 구체화한 과정

### 3.1 사용자가 제시한 상황

1. 처음에는 A라고 알려줬던 선임이 나중에는 B라고 말한다.
2. 몰라서 물어보면 지적받고, 묻지 않으면 모르면 물어보라고 지적받는다.
3. 사람에게 질문하기 전에 업무의 맥락과 관련 내용을 쉽게 찾고 싶다.
4. 신입사원뿐 아니라 다른 임직원도 편하게 쓰는 사내 서비스를 만들고 싶다.

이를 다음과 같이 연결했다.

| 내용 | 문제 정의에서의 역할 | 서비스가 도울 수 있는 부분 |
|---|---|---|
| 설명이 A에서 B로 바뀜 | 정보 일관성과 변경 이력 문제 | 현재 안내, 출처, 변경 시점 확인 |
| 질문해도 하지 않아도 지적받음 | 질문에 대한 심리적 부담 | 스스로 확인할 경로 제공 |
| 질문 전에 맥락과 자료 찾기 | 해결 방식의 가설 | 관련 문서와 앞뒤 절차 안내 |
| 모든 임직원이 사용 | 장기적인 제품 방향 | 다른 직원과 업무로 적용 범위 확대 |

### 3.2 문제 정의 초안

> 신입 직원은 업무 안내가 여러 곳에 흩어져 있고 설명이 서로 다를 때, 현재 따라야 할 기준을 확인하기 어렵다. 사람에게 반복해서 질문하는 부담 때문에 확인을 미루거나 잘못된 방식으로 업무를 진행할 수 있다.

### 3.3 서비스가 제공하려는 결과

> 업무 질문에 대해 관련 자료와 맥락을 찾아주고, 출처·적용 조건·확인 시점을 보여준다. 근거가 부족하거나 자료가 충돌하면 담당자에게 확인할 내용을 정리해준다.

서비스가 안내할 수 있는 범위는 기록된 자료를 바탕으로 한 기준 확인과 절차 안내다. 기록되지 않은 지시나 해결되지 않은 문서 충돌은 담당자 확인으로 연결해야 한다.

## 4. 첫 사용자와 핵심 질문

### 4.1 현재 사용자 접근 상황

- 아직 실제 사용을 부탁할 수 있는 신입사원이 없다.
- 처음에는 특정 직군도 정해지지 않았다.
- 실제 사내 자료를 확보한 상태가 아니다.
- 가상 회사 자료로 첫 검증을 시작하기로 했다.

첫 사용자 후보는 접근 가능성, 문제의 구체성, 결과를 확인할 수 있는지를 기준으로 좁혀 가는 방식을 논의했다.

### 4.2 첫 검증 사용자

> 의류 쇼핑몰 개발팀에 합류해 처음으로 일반 버그 수정 업무를 맡은 신입 개발자.

제품 전체의 대상은 다양한 조직의 임직원이다. 위 사용자는 첫 자료와 시나리오를 구체화하기 위한 검증 대상이다.

### 4.3 사용자가 선택한 핵심 질문

> 이 업무는 이전에 어떻게 처리했고, 지금 따라야 할 기준과 절차는 무엇인가요? 관련 자료와 담당자도 알려주세요.

### 4.4 답변에 필요한 내용

1. 이전에 어떤 상황에서 어떻게 처리했는지 설명한다.
2. 현재 기준의 근거 문서와 적용 시점을 보여준다.
3. 지금 해야 할 행동과 필요한 승인 절차를 안내한다.
4. 관련 원문과 담당 역할 또는 확인 경로를 제공한다.
5. 자료 누락, 충돌, 불명확한 적용 조건을 표시한다.

과거 처리 방식이 현재에도 유효한지는 별도로 판단해야 한다. 작성일뿐 아니라 문서 승인 상태, 시행일, 적용 대상과 대체 관계를 확인해야 한다.

## 5. 결정한 첫 업무와 가상 회사 배경

### 5.1 업무 선택 과정

처음에는 교육 수강 신청·교육비 지원, 장비 신청·대여·반납, 개발 환경 접근 권한 신청을 후보로 제시했다. 교육비 지원은 당시 추천 후보였으며 확정되지 않았다.

이후 사용자가 의류 쇼핑몰 개발팀을 배경으로 정했고, 일반 버그 수정·배포 절차를 첫 검증 업무로 선택했다.

### 5.2 가상 회사 설정 초안

회사 이름과 아래 세부 설정은 대화에서 제안한 초안이다.

| 항목 | 설정 |
|---|---|
| 회사 이름 | 옷담 |
| 사업 | 자체 웹사이트에서 의류와 패션 잡화 판매 |
| 조직 | 상품기획, 마케팅, 고객지원, 물류, 개발팀 |
| 개발팀 업무 | 상품·주문·쿠폰 기능 개발, 오류 수정, 서비스 운영 |
| 첫 검증 업무 | 일반 버그 수정·배포 |
| 사용자의 막힘 | 과거 처리 이유, 현재 검토·배포 절차, 관련 자료와 담당자 확인 |

실제 개발할 제품은 사내 업무 안내 웹서비스다. 의류 쇼핑몰 회사는 자료와 업무 상황을 제공하는 가상 배경이다.

### 5.3 범용 제품을 위한 방향

조직, 업무, 적용 대상, 문서 종류, 상태, 적용 기간, 담당 역할, 연결 근거를 공통 형식으로 관리하는 방향을 제안했다.

개발팀의 PR 검토·배포 승인처럼 특정 업무에 쓰이는 용어와 단계는 각 조직의 자료에 담는다. 업무별 절차의 순서와 승인 조건도 해당 조직의 자료에서 확인해야 한다.

| 개발팀의 사례 | 다른 업무에서 대응할 수 있는 내용 |
|---|---|
| 버그 수정 요청 | 구매 요청, 계약 검토 요청, 고객 문의 |
| 코드 검토 | 내용 검토, 서류 검토 |
| 배포 승인 | 구매 승인, 계약 승인 |
| 배포 결과 확인 | 납품 확인, 처리 결과 확인 |

답변과 검색 근거는 사용자가 접근할 수 있는 해당 조직의 자료를 기준으로 제공한다. 배포 전에는 다른 직무의 작은 자료 묶음도 사용해 개발팀에만 맞춘 가정이 남아 있는지 확인하는 방식을 제안했다.

## 6. 가상 자료를 만드는 방식

### 6.1 먼저 제안한 자료 목록

| 구분 | 자료 | 필요한 내용 |
|---|---|---|
| 공통 배경 | 회사·조직 소개 | 부서별 역할과 협업 관계 |
| 공통 배경 | 개발팀 담당 업무 | 주문·상품·쿠폰 영역의 담당 역할 |
| 공통 배경 | 업무 용어집 | SKU, 기획전, 쿠폰, 주문 상태 등의 뜻 |
| 공통 배경 | 시스템 개요 | 쇼핑몰 화면, 관리자 화면, 서버의 관계 |
| 업무 근거 | 이전 지침 | 과거에 적용했던 절차 |
| 업무 근거 | 현재 지침 | 지금 적용하는 검토·테스트·승인 절차 |
| 업무 근거 | 변경 공지 | 변경 내용, 이유, 시행일 |
| 업무 근거 | 과거 처리 기록 | 당시 상황, 처리 내용, 결과 |
| 업무 근거 | 확인 목록·요청서 | 준비할 정보와 제출 순서 |
| 업무 근거 | 차기 절차 초안 | 아직 승인되지 않은 변경 제안 |

현재 대화에서 본문까지 작성한 것은 이전 지침, 현재 지침, 과거 처리 사례 세 개다. 나머지는 자료 구성 제안이다.

### 6.2 문서에 붙일 설명 정보

문서의 ID, 종류, 버전, 상태, 적용 대상, 작성·승인일, 시행일·종료일, 책임자·승인자, 연결 문서를 함께 기록한다. 이런 설명 정보를 메타데이터라고 한다.

작성일, 시행일, 사건 발생일을 구분한다. 자료의 상태와 날짜는 서로 다른 판단 근거이므로 함께 확인해야 한다.

평가 기준일은 문서 정리일과 별개로 고정한 가상 시점이다.

## 7. 가상 문서 1 — 이전 일반 버그 수정·배포 지침

| 문서 ID | `POL-CHANGE-001-V1` |
| 조직·부서 | 옷담 / 개발팀 |

| 문서 종류 | 업무 지침 |
| 버전 | 1.0 |

| 문서 책임자 | 개발팀장 |
| 후속 문서 | `POL-CHANGE-001-V2` |

### 7.1 목적과 적용 범위

개발팀에서 발견한 일반 버그를 수정하고 운영 서비스에 반영하는 절차를 정한다.

일반 버그는 영향 범위가 확인되어 있고, 서비스 전체 중단이나 고객의 실제 결제 금액 오류 등 중대한 문제가 발생하지 않은 오류를 뜻한다.

보안 문제, 개인정보 노출, 실제 결제 오류, 데이터 손상, 긴급 장애에는 개발팀장에게 상황을 전달하고 별도 대응을 확인한다.

### 7.2 처리 절차

1. **업무 기록 작성**  
   작업자는 오류 발생 화면, 재현 방법, 기대한 결과와 실제 결과를 업무 기록에 작성한다.

2. **영향 범위 확인**  
   어떤 화면과 기능에 영향을 주는지 확인한다. 영향 범위를 판단할 수 없으면 개발팀장에게 먼저 확인한다.

3. **수정과 자체 확인**  
   작업자는 코드를 수정하고 개발 환경에서 오류가 해결됐는지 확인한다. 관련 기능이 정상 동작하는지도 확인한다.

4. **업무 담당자 확인**  
   해당 기능의 업무 담당자에게 수정 전후 결과를 보여주고, 의도한 업무 규칙과 맞는지 확인받는다.

5. **배포 요청과 수행**  
   확인 결과를 개발팀장에게 전달한다. 개발팀장의 배포 승인 후, 지정된 배포 수행자가 운영 환경에 반영한다.

6. **배포 결과 기록**  
   배포 버전, 수행자, 시각, 확인 결과를 업무 기록에 남긴다. 배포 후 문제가 발생하면 개발팀장에게 즉시 알린다.

### 7.3 검토 방식

PR은 변경 내용을 동료에게 검토받기 위한 요청이다. 이 지침에서 동료 코드 검토는 작업자가 필요하다고 판단하거나 개발팀장이 요청하면 진행한다. 테스트 전용 환경의 별도 검증도 필요에 따라 진행한다.

### 7.4 당시 담당 역할

| 역할 | 책임 |
|---|---|
| 작업자 | 오류 기록, 수정, 자체 확인 |
| 업무 담당자 | 수정 결과가 업무 규칙과 맞는지 확인 |
| 개발팀장 | 처리 범위 판단, 배포 승인 |
| 배포 수행자 | 승인된 변경 반영, 배포 결과 기록 |

### 7.5 현재 사용 시 확인 사항

이 지침은 2026년 9월 30일까지 적용됐다. 현재 업무의 처리 방법을 결정할 때는 후속 문서의 적용 대상과 시행일을 확인한다.

### 8.1 목적과 적용 범위

일반 버그 수정 과정에서 동료 검토, 테스트 환경 확인, 배포 승인을 기록으로 남긴다.

2026년 10월 1일 이후 배포 승인을 요청하는 일반 버그 수정에 적용한다. 시행일 전에 시작한 작업도 배포 승인 요청이 시행일 이후라면 이 지침을 따른다.

보안 문제, 개인정보 노출, 실제 결제 오류, 데이터 손상, 긴급 장애는 별도 대응 확인이 필요하다. 이 지침에 없는 긴급 절차는 담당자에게 확인한다.

### 8.2 이전 지침에서 변경된 사항

| 항목 | 이전 지침 | 현재 지침 |
|---|---|---|
| 동료 코드 검토 | 필요할 때 진행 | PR 검토 필수 |
| 테스트 환경 확인 | 필요에 따라 진행 | 배포 전 필수 |
| 승인 요청 자료 | 작업 결과 중심 | PR·테스트 결과·되돌리기 계획 포함 |
| 승인 기록 | 업무 기록에 남김 | 승인 대상 버전까지 명시 |
| 승인 후 수정 | 별도 규정 없음 | 변경 내용에 대한 재확인 필요 |

### 8.3 처리 절차

1. **업무 기록 작성과 분류**  
   작업자는 증상, 재현 방법, 기대 결과, 영향 범위와 확인 근거를 작성한다. 일반 버그에 해당하는지 불명확하면 개발팀장에게 확인한다.

2. **업무 규칙 확인**  
   관련 지침과 업무 담당자를 확인한다. 과거 처리 사례와 현재 지침이 다르면 적용 기간과 대상부터 확인한다. 해결되지 않는 충돌은 담당자에게 확인하고 결과를 기록한다.

3. **작업용 브랜치에서 수정**  
   브랜치는 다른 작업과 구분해 코드를 수정하는 공간이다. 작업자는 수정 내용과 확인 방법을 업무 기록에 연결한다.

4. **PR 생성과 동료 검토**  
   PR에 변경 이유, 영향 범위, 확인 결과를 작성한다. 작성자 이외의 개발자 한 명 이상이 검토하고 승인해야 한다.

5. **테스트 환경 검증**  
   운영 반영 전 확인을 위한 환경에서 원래 오류 해결 여부, 관련 기존 기능의 정상 동작 여부, 확인하지 못한 범위를 검증한다. 업무 규칙에 관한 결과는 해당 업무 담당자에게 확인받는다.

6. **배포 승인 요청**  
   작업자는 개발팀장에게 업무 기록, 승인된 PR, 배포할 코드 버전, 테스트 결과, 확인하지 못한 범위, 배포 후 확인 항목, 이전 버전으로 되돌리는 계획을 제출한다. 개발팀장은 승인 대상 버전과 배포 수행자를 기록한다. 코드 검토자와 배포 승인자는 같은 사람일 수 있지만, 작업자가 자기 변경의 유일한 검토자·승인자가 될 수는 없다.

7. **배포 수행**  
   지정된 수행자가 승인된 버전을 반영한다. 승인 후 코드가 변경됐다면 영향을 받는 검토·테스트를 다시 진행하고 새 버전의 승인을 받는다.

8. **배포 후 확인과 종료**  
   배포 직후 오류 재현 여부와 관련 기능을 확인하고, 이후 15분 동안 관련 오류 기록을 관찰한다. 결과, 배포 시각, 버전을 업무 기록에 남긴다.

### 8.4 배포 후 문제가 발생한 경우

원래 오류가 계속 발생하거나 새로운 문제가 발견되면 추가 배포를 중단하고 배포 승인자에게 알린다.

사전 승인된 되돌리기 조건에 해당하면 지정된 수행자가 계획을 실행한다. 계획의 적용 여부가 불명확하면 배포 승인자의 판단을 받는다. 되돌린 후에도 정상 동작을 다시 확인하고 결과를 기록한다.

### 8.5 현재 담당 역할과 확인 경로

| 역할 | 책임 | 가상 확인 경로 |
|---|---|---|
| 업무 담당자 | 업무 규칙과 결과 확인 | 업무 기록에 지정된 기능 담당자 |
| 코드 검토자 | 변경 내용과 영향 검토 | PR에 지정된 동료 개발자 |
| 배포 승인자 | 배포 여부와 대상 버전 승인 | 개발팀장 / ‘개발팀 배포 요청’ 채널 |
| 배포 수행자 | 승인 버전 반영과 결과 확인 | 승인 기록에 지정된 수행자 |

### 9.1 발생 상황

일부 기획전 상품의 상세 화면에서 쿠폰을 적용할 수 있다는 안내가 잘못 표시됐다.

확인 결과, 화면의 안내 문구에 문제가 있었다. 서버의 쿠폰 적용 판정과 실제 주문·결제 금액은 정상 동작하는 것으로 확인됐다. 당시 개발팀장은 확인된 영향 범위를 바탕으로 일반 버그로 분류했다.

다른 사건에서 영향 범위가 확인되지 않았다면 별도로 분류를 확인해야 한다.

### 9.2 당시 처리 과정

1. 고객지원팀이 잘못된 쿠폰 안내 화면을 개발팀에 전달했다.
2. 작업자가 대상 상품과 재현 조건을 업무 기록에 정리했다.
3. 작업자가 안내 문구를 결정하는 화면 로직을 수정했다.
4. 개발 환경에서 수정 결과와 관련 화면을 확인했다.
5. 쿠폰 업무 담당자가 해당 상품의 쿠폰 적용 규칙과 수정 결과가 일치함을 확인했다.
6. 개발팀장이 배포를 승인했다.
7. 지정된 수행자가 운영 환경에 반영하고 결과를 기록했다.

### 9.3 당시 검토·확인 기록

- 별도 PR 동료 검토는 진행하지 않았다.
- 테스트 전용 환경에서의 별도 검증은 진행하지 않았다.
- 작업자의 개발 환경 확인과 업무 담당자 확인을 진행했다.
- 당시 적용 지침에서는 PR 검토와 테스트 전용 환경 검증을 일괄 필수로 요구하지 않았다.

### 9.4 처리 결과와 확인 한계

배포 직후 같은 조건에서 잘못된 안내가 재현되지 않았다. 주문·결제 금액이 정상 동작하는지도 다시 확인했다.

이 기록의 관찰 범위는 배포 당일 확인 결과다. 배포 다음 날 이후의 장기 관찰 결과는 기록되어 있지 않다.

### 9.5 현재 유사 업무를 처리할 때

이 사례는 2026년 9월 당시 어떤 방식으로 처리했는지를 보여준다.

2026년 10월 1일 이후 배포 승인을 요청하는 작업은 `POL-CHANGE-001-V2`의 적용 여부를 확인해야 한다. 현재 지침이 적용된다면 PR 검토와 테스트 환경 검증을 진행해야 한다.

같은 쿠폰 증상이라도 실제 결제 금액 오류가 포함돼 있으면 별도 대응을 확인한다.

## 11. 학습과 개발 진행 방식

### 11.1 초기 단계 로드맵

| 단계 | 해야 할 일 | 완료 기준 | 연결할 학습 |

| 피드백·개선 | 사용 과정 확인과 문제 수정 | 개선 이유와 결과를 기록함 | 디버깅, 성능 측정, 회고 |

짧은 주기로 목표 정하기, 개발하기, 함께 시연하기, 다음 개선 정하기를 반복하는 방식을 제안했다. 1주 주기를 출발점으로 제시했으며 실제 참여 시간과 일정은 아직 정하지 않았다.

### 11.2 Git 협업 방식 제안

작업 설명 작성 → 작업용 브랜치 생성 → 수정 → 커밋 → PR → 동료 검토 → 병합.

- `main`은 실행 가능한 상태로 유지한다.
- 작업마다 짧게 사용하는 브랜치를 만든다.
- PR에 변경 이유와 확인 방법을 적는다.
- 다른 팀원 한 명이 확인한 뒤 합친다.
- 비밀번호와 API 키는 저장소에 올리지 않는다.

이 규칙은 실제 프로젝트 팀을 위한 제안이다. 가상 회사의 이전·현재 지침과 별도로 팀에서 합의해야 한다.

Git 학습 순서는 `status`, `diff`, `add`, `commit`, `log`에서 시작해 브랜치, PR, 충돌 해결, 변경 되돌리기로 이어가는 방식을 제안했다.

### 11.3 CS 학습 연결

| 개발 중 생기는 질문 | 공부할 내용 |
|---|---|
| 버튼을 눌렀는데 서버는 어떻게 알까? | HTTP 요청·응답, JSON, 상태 코드 |
| 새로고침하면 데이터가 왜 사라질까? | 메모리와 영구 저장, DB |
| 다른 사용자의 기록을 보면 안 되는데? | 인증과 인가 |
| 같은 요청이 두 번 오면 어떻게 될까? | 중복 처리, 트랜잭션 |
| 내 PC와 서버의 실행 결과가 왜 다를까? | 실행 환경, 프로세스, 포트, 환경변수 |
| 오류가 나면 어디부터 봐야 할까? | 브라우저 개발자 도구, 서버 로그 |
| 응답이 느린 이유는 무엇일까? | 네트워크·DB·외부 API 시간 측정 |

매주 겪은 문제, 원인, 해결 방법, 연결된 CS 개념을 기록하는 방식을 제안했다.

### 11.4 AI 품질 확인

근거 자료, 자료에 없는 질문에 대한 응답, 정답 기준, 자료 접근 범위, 응답 시간, 사용 비용을 확인해야 한다고 논의했다.

자료에 근거가 있으면 출처와 함께 안내하고, 부족하거나 충돌하면 그 상황을 알린 뒤 확인할 내용을 정리하는 동작을 지향한다.

사용자는 실제 IT 트렌드도 반영하기를 원한다. 현재까지 최신 기술 조사나 기술 스택 선정은 진행하지 않았고, 구체적인 도구는 이후 선정할 예정이다.

## 12. 다음 기획 작업

### 12.1 문서부터 개발 작업까지

| 순서 | 산출물 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 1 | 사용자·문제·첫 업무를 적은 1쪽 문서 | 세 사람이 같은 범위를 설명함 |
| 2 | 문서 목록과 날짜·규칙 관계표 | 현재 기준과 과거 사례가 구분됨 |
| 3 | 질문·기대 답변·근거 문서 목록 | 사람이 정답 여부를 판단할 수 있음 |
| 4 | 질문부터 원문 확인까지의 화면 스케치 | 정상·자료 없음·충돌 상황을 설명함 |
| 5 | 기능별 동작과 완료 조건 | 구현하고 확인할 내용이 명확함 |
| 6 | 데이터 구조, API, 검색·AI 처리, 배포 설계 | 선택 이유와 대안을 설명함 |
| 7 | 작게 나눈 작업과 담당자 | 각 작업의 결과를 시연할 수 있음 |

제안한 첫 화면 흐름은 질문 입력, 필요한 조건 추가 확인, 답변·근거 확인, 원문 또는 담당자 확인이다.

### 12.2 바로 진행할 팀 작업

1. 세 사람이 가상 문서 세 개를 읽는다.
2. 초기 평가 질문 다섯 개에 각자 독립적으로 답한다.
3. 답이 달라지는 부분의 문서와 규칙을 수정한다.
4. 합의한 기대 답변과 근거를 평가 목록으로 정리한다.

문서 작성 단계의 역할로는 사용자의 업무 범위·규칙 정리, 팀원 1의 사용자 질문·화면 흐름 작성, 팀원 2의 문서·평가 초안 작성을 제안했다. 실제 분담은 팀에서 정한다.

## 13. 현재 결정 상태

### 13.1 사용자가 명시한 방향과 결정

- 세 명이 실제 프로젝트 과정을 배우며 진행한다.
- 웹 브라우저로 사용할 수 있게 배포한다.

- 배포 시에는 산업과 직무에 관계없이 사용할 수 있는 방향을 원한다.
