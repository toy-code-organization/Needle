- 목적: 우주인 발표자료에서 현재 온보딩 RAG 서비스에 활용할 기술과 운영 방식을 정리한다.

## 3. DB 연결 관리

### 3.1 쉬운 설명과 문제

DB 연결은 서버가 DB와 대화하는 통로다. 사용 가능한 통로 수에는 제한이 있다. AI가 오래 답변하는 동안 통로를 계속 잡고 있으면 다른 사용자의 문서 조회나 대화 저장도 기다리게 된다.

트랜잭션은 여러 DB 변경을 함께 성공하거나 실패하게 만드는 단위다. 단순히 코드를 `async`로 바꿔도 DB 연결이나 트랜잭션을 오래 유지하면 문제는 남는다.

### 3.2 적용 방식

질의응답은 다음 경계를 둔다.

1. Spring에서 인증·권한을 확인하고 필요한 데이터를 조회한다.
2. 조회에 사용한 DB 세션·연결을 정리한다.
3. FastAPI 검색 경로에서도 필요한 검색 결과를 메모리의 일반 데이터로 옮긴 뒤 DB 연결을 반환한다.
4. Ollama 답변 생성과 SSE 전송을 수행한다.
5. 답변 완료 후 필요한 결과를 새 짧은 트랜잭션으로 저장한다.

문서 worker도 작업 확보와 결과 저장에만 짧은 트랜잭션을 사용한다. 원본 다운로드, 텍스트 추출, 임베딩 생성 중에는 작업 확보용 트랜잭션을 유지하지 않는다.

주의할 점:

- SSE 응답이 끝날 때까지 요청 단위 DB 세션이 살아 있는지 확인한다.
- Spring의 AI 통신 코드를 긴 `@Transactional` 범위에 넣지 않는다.
- 연결 반환 전에 필요한 필드를 읽어 두고, 반환 후 ORM 지연 조회에 의존하지 않는다.
- 문서가 처리 중 수정·삭제되면 저장·활성화 직전에 버전과 사용 가능 상태를 다시 검사한다.
- 권한 변경 반영 시점과 생성 중 답변의 중단 기준은 백엔드와 계약한다.

### 3.3 검증

- 모델 응답을 의도적으로 지연시키고 DB 활성 연결 수와 열린 트랜잭션을 확인한다.
- 동시 질문 1·5·10·20건에서 오류율, 첫 토큰 시간, 전체 완료 시간, DB 연결 대기 시간을 기록한다.
- 스트리밍 중 취소·모델 오류·시간 초과 후 연결이 반환되는지 확인한다.
- 모델 자체의 처리 용량 초과와 DB 연결 고갈을 구분해 기록한다.
- 첫 토큰·전체 완료 목표는 기존 평가 기준을 출발점으로 삼되 실제 장비에서 확정한다.

## 4. 복구 가능한 문서 작업 대기열

### 4.1 쉬운 설명과 목표

문서를 올린 즉시 모든 AI 처리를 끝내려 하면 요청이 오래 걸린다. 먼저 처리할 일을 저장하고, 별도 worker가 가져가서 수행하게 한다. 서버를 껐다 켜도 남은 일을 이어 할 수 있어야 한다.

파일 업로드 성공과 검색 준비 완료는 다른 상태다. 화면에도 대기·처리 중·검색 가능·실패를 구분해 보여준다.

### 4.2 시작안: PostgreSQL 작업 테이블

현재 사용하는 PostgreSQL에 작업 테이블을 두는 방식을 우선 검토한다. Redis 운영을 추가하지 않고도 작업을 영구 저장할 수 있다.

아래는 설계 후보이며 실제 테이블명·컬럼명·스키마 소유자는 백엔드와 AI팀이 합의한다.

| 필드 | 역할 |
| --- | --- |
| `job_id` | 작업 식별자 |
| `document_id`, `document_version` | 처리할 원본과 버전 |
| `pipeline_version` | 추출·청킹·임베딩 설정 묶음의 버전 |
| `status` | `PENDING`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `CANCELLED` |
| `attempt_count`, `next_retry_at` | 시도 횟수와 다음 시도 가능 시각 |
| `lease_expires_at` | worker가 이 작업을 맡는 유효 시간 |
| `claim_token` | 현재 작업 확보를 식별하는 값. 오래된 worker의 저장 차단 |
| `error_code`, `request_id` | 실패 분류와 연계 추적 |
| `created_at`, `updated_at` | 생성·갱신 시각 |

처리 순서:

1. 문서 메타데이터 저장과 작업 등록 사이에 유실이 없도록 한다. 같은 DB 트랜잭션으로 처리하거나, 분리된 경우 누락 복구 방식을 둔다.
2. worker가 처리 가능한 작업을 짧은 트랜잭션에서 확보한다. 여러 worker를 운영하면 `FOR UPDATE SKIP LOCKED`를 검토한다.
3. `PROCESSING` 상태, 유효 시간, 새 `claim_token`을 저장하고 트랜잭션을 끝낸다.
4. 원본 다운로드·텍스트 추출·청킹·임베딩을 수행한다. 오래 걸리는 작업은 확보 유효 시간을 갱신한다.
5. 현재 `claim_token`과 문서 버전·사용 상태를 확인한 뒤 결과를 저장한다.
6. 완성된 버전의 검색 데이터만 활성화하고 작업을 완료한다.
7. worker가 죽으면 유효 시간이 지난 작업을 다시 확보한다. 이전 worker가 늦게 돌아와도 과거 토큰으로 결과를 활성화할 수 없어야 한다.

### 4.3 중복·재시도·버전 규칙

- 같은 문서·원본 버전·파이프라인 버전의 작업은 중복 등록을 제한한다. 파이프라인 버전이 바뀐 재인덱싱은 허용한다.
- 재시도해도 같은 조각이 반복 삽입되지 않도록 조각 키와 고유 제약을 정한다.
- 네트워크 일시 장애는 간격을 늘려 재시도한다. 잘못된 파일·지원하지 않는 형식은 무한 재시도하지 않는다.
- 최대 재시도 횟수와 간격은 설정으로 관리하고 팀이 실제 값을 결정한다.
- 새 버전 처리 중 구버전을 계속 제공할지 즉시 제외할지는 정책으로 합의한다. 삭제·사용 중지된 문서는 새 답변 근거에서 제외한다.
- 작업 상태, 벡터 저장, 검색 버전 활성화 사이의 실패를 복구할 수 있어야 한다.

### 4.4 Redis Streams를 선택할 경우

발표자료에는 Redis 큐·Stream 구성이 표시되어 있다. 구체적인 복구 구현까지 검증한 것은 아니다. 우리 팀이 Redis Streams를 도입한다면 다음 항목을 별도 구현한다.

- consumer group으로 worker의 작업을 분배한다.
- 결과를 영구 저장한 뒤 `XACK`로 완료를 알린다.
- ACK되지 않은 작업을 확인하고, 멈춘 worker의 작업을 회수한다.
- 같은 작업이 다시 전달되어도 중복 결과가 생기지 않게 한다.
- Redis 영속성·복구·메시지 보존 정책을 정한다. Redis 사용만으로 작업 무손실이 보장되지는 않는다.
- DB의 문서 등록과 Redis 메시지 발행 사이의 누락을 outbox 또는 재조정 작업으로 복구한다.

### 4.5 완료 기준

- 작업 확보 직후, 임베딩 도중, 결과 저장 직후 worker를 종료해도 재시작 후 일관된 상태로 복구된다.
- 같은 등록 요청을 두 번 보내거나 작업을 재전달해도 활성 검색 데이터가 중복되지 않는다.
- 구버전 작업이 새 버전보다 늦게 끝나도 현재 버전을 덮어쓰지 않는다.
- 문서를 처리 중 삭제·중지하면 늦게 완료된 작업이 문서를 다시 검색 가능하게 만들지 않는다.
- 실패 사유와 재시도 가능 여부를 관리자에게 표시한다.

## 5. 모니터링과 로그

### 5.1 쉬운 설명과 구성

사용자가 느리다고 할 때 검색이 느린지, 모델이 느린지, 작업이 밀린 것인지 구분하기 위한 장치다.

처음에는 구조화된 로그와 시간 측정부터 시작한다. 배포 검증 단계에서 Prometheus 지표 수집과 Grafana 대시보드를 검토한다. Loki·Dozzle까지 한 번에 추가할 필요는 없다.

### 5.2 수집할 지표

| 지표 | 측정 범위·목적 |
| --- | --- |
| 질문 임베딩 시간 | 질문 벡터 생성 지연 |
| 검색 시간 | DB 검색과 필터 적용 구간 |
| 첫 토큰 시간 | 질문 접수부터 첫 답변 토큰 수신까지. 서버 측·사용자 화면 측 측정 구간을 구분 |
| 전체 답변 시간 | 질문 접수부터 완료 또는 실패까지. 결과별 분류 |
| 질문 오류·타임아웃 수 | 검색·모델·통신 장애 분류 |
| 대기 작업 수·가장 오래 기다린 시간 | 인덱싱 적체 확인 |
| 인덱싱 시간·실패·재시도 수 | 문서 처리 상태 확인 |
| DB 연결 사용량·대기 시간 | 연결 고갈 여부 확인 |

시간 지표는 Histogram을 검토한다. 평균만 보지 않고 p95도 확인한다. p95는 요청 95%가 그 시간 이내에 끝났다는 뜻이다. 표본 수와 동시 요청 수도 함께 남긴다.

### 5.3 로그 규칙과 완료 기준

- Spring에서 받은 `requestId`를 FastAPI·worker 기록에 연결한다. 문서 작업은 `job_id`도 사용한다.
- 일반 로그에는 요청 ID, 작업 ID, 문서 ID, 처리 단계, 소요 시간, 오류 코드 중심으로 기록한다.
- 질문·답변·문서 원문, 인증 토큰, S3 서명 URL은 일반 로그에 남기지 않는다.
- Prometheus 라벨에는 요청 ID·사용자 ID·질문 문자열을 넣지 않는다. 요청마다 다른 값이 쌓이면 지표 저장량이 급증한다.
- 문서 형식·결과 상태·처리 단계 등 값 종류가 제한된 라벨을 사용한다.
- 의도적으로 모델 장애와 인덱싱 실패를 만들고 지표·로그에서 해당 단계를 찾을 수 있으면 1차 검증 완료다.
- 모니터링·로그 화면의 접근권한과 보존 기간은 운영 담당자와 합의한다.

## 6. 하이브리드 검색: 검색 실패를 확인한 뒤 실험

### 6.1 왜 필요한가

의미 검색은 표현이 달라도 비슷한 내용을 찾는 데 사용한다. 반면 `POL-CHANGE-001-V2`, 오류 코드, 상품 코드처럼 정확한 문자열이 중요한 질문은 별도 문자열 검색이 도움이 될 수 있다.

발표 31쪽은 두 검색의 결과 비교다. 두 방식을 결합한 구현이 확인된 것은 아니다. 하이브리드 검색은 이를 바탕으로 한 우리 팀의 추가 제안이다.

### 6.2 실험 방식

1. 권한·문서 사용 상태·적용 버전 조건을 두 검색에 동일하게 적용한다.
2. pgvector로 의미 검색 후보를 찾는다.
3. 문서 ID·코드는 정확 일치 검색, 본문은 PostgreSQL 전문 검색 등으로 후보를 찾는다.
4. 중복을 제거하고 RRF처럼 검색 순위를 결합하는 방식을 실험한다. RRF는 서로 점수 범위가 다른 검색의 순위를 이용해 결과를 합치는 방법이다.
5. 상위 근거 조각을 답변 모델에 전달한다.

한국어 본문은 기본 전문 검색 설정만으로 충분한지 별도 확인해야 한다. 검색 후보 수·결합 방식은 평가로 정한다. 발표 31쪽의 순서대로 키워드 결과가 없을 때만 의미 검색할지, 항상 둘을 결합할지도 비교 대상이다.

### 6.3 도입 판단

- 같은 평가 질문으로 기본 의미 검색과 비교한다.
- 정답 문서 Top 5 포함률, 정확한 코드 질문의 성공률, 검색 시간 변화를 기록한다.
- 실제로 결과가 개선되고 응답 지연이 허용 범위에 들어올 때 도입한다.
- 답이 없는 질문을 포함해 잘못된 근거로 답변하는 비율도 함께 확인한다.
- 기존 평가 목록에서 답이 있는 질문의 검색 지표와 답이 없는 질문의 거절 지표는 분리 계산한다.

## 7. Qwen3-VL: 이미지 문서 처리 확장 후보

### 7.1 쉬운 설명과 적용 대상

현재 Qwen3 8B는 검색한 텍스트를 받아 답변하는 역할이다. Qwen3-VL은 이미지와 텍스트를 함께 입력받는 별도 모델이다. 이름이 비슷해도 현재 모델에 이미지를 바로 넣는다는 뜻은 아니다.

적용 후보는 스캔 PDF, 화면 캡처 중심의 매뉴얼, 텍스트 추출이 안 되는 표·도표다. 정상적으로 텍스트를 읽을 수 있는 문서까지 모두 이미지로 처리하지 않는다.

### 7.2 실험 순서

1. 실제 업무 자료에서 대표 페이지를 선정한다. 작은 글씨·한국어·표·번호가 있는 사례를 포함한다.
2. 기존 문서 추출 방식으로 읽을 수 있는지 먼저 확인한다.
3. 읽기 어려운 페이지만 OCR 또는 Qwen3-VL 후보와 비교한다.
4. 추출 결과에 원본 문서 ID·버전·페이지를 연결한다. 영역 좌표를 제공할 수 있는 경우 해당 위치도 보존한다.
5. 검증한 추출 텍스트를 기존 청킹·임베딩 파이프라인에 넣는다.

처리 과정에서 중요한 조건·수치·부정 표현이 사라질 수 있으므로 요약문만을 검색 원문으로 삼지 않는다. 도표 설명은 AI 해석임을 구분하고, 출처 화면에서 원본을 확인할 수 있어야 한다.

### 7.3 검증과 도입 조건

- 사람의 원본 판독 결과와 비교해 금액·날짜·번호·처리 순서·예외 조건의 정확성을 확인한다.
- 페이지별 처리 시간, GPU 메모리 사용량, 동시 질의응답 지연을 측정한다.
- 부정확한 추출 결과는 검색 가능 상태로 자동 승격하지 않는 정책을 정한다.
- 원본·추출 텍스트·이미지 임시 파일에 같은 문서 접근권한과 삭제 정책을 적용한다.
- 로컬 모델 실행과 승인 정책을 확인한다. 외부 API 전환은 기존 사내 문서 처리 정책에 맞춰 별도 결정한다.
- 실제 이미지 자료 수요와 운영 가능한 장비가 확인됐을 때 도입한다.

## 8. 팀별 조율 항목과 실행 순서

| 담당 | 조율할 내용 |
| --- | --- |
| AI | worker 작업 확보·복구, 임베딩 처리, 검색 평가, 모델 호출과 DB 세션 범위 |
| 백엔드 | 문서 버전·권한 정본, 작업 등록 연계, 결과 상태 반영, 대화 저장 트랜잭션 |
| 프론트엔드 | 업로드 완료·처리 중·검색 가능·실패 표시, 답변 취소·오류 상태 |
| 인프라 담당 | DB 연결 수, 모델 장비, worker 재시작, 지표 수집·접근권한·보존 |

실행은 다음 순서로 진행한다.

1. 권한 있는 문서 하나로 기본 검색·답변·출처 흐름을 완성한다.
2. DB 연결의 생명주기를 확인하고 느린 모델 호출과 분리한다.
3. 문서 작업을 영구 저장하고 worker 종료·재시도·버전 역전·삭제 시나리오를 검증한다.
4. 단계별 지표를 수집하고 동시 요청 부하를 측정한다.
5. 평가에서 발견한 검색 실패를 바탕으로 하이브리드 검색을 실험한다.
6. 이미지 문서 수요가 확인되면 별도 추출 실험을 수행한다.

각 단계는 개념 설명, 입출력 정의, 의사코드, 직접 구현, 검증 결과 기록, 동료 리뷰 순서로 마무리한다. 이 문서 추가 자체가 기능 구현 완료를 뜻하지 않는다.
