## 1. 프로젝트 한 줄 요약

작은 의류 회사의 임직원이 사내 문서와 패션 용어를 근거·출처와 함께 검색하고, 신입사원의 온보딩과 기존 직원의 인수인계를 돕는 사내 RAG 기반 AI 워크스페이스를 만든다.

## 2. 개발 방식 원칙

- 개발자는 코드를 직접 입력하고 이해하면서 구현한다.
- AI 도구는 개념 설명, 입출력 정의, 의사코드, 테스트 사례, 오류 힌트, 작성한 코드 리뷰에 사용한다.
- AI 도구에 전체 기능 구현을 맡기지 않는다.
- 한 번에 작은 기능 하나만 `이해 → 의사코드 → 직접 구현 → 테스트 → 설명` 순서로 끝낸다.
- 설치된 `Qwen3 8B`는 서비스 답변 모델이며 개발 코딩 에이전트가 아니다.

AI에게 요청할 기본 문장:

```text
전체 코드를 작성하지 말고 이번 단계의 개념, 입출력, 의사코드, 테스트 사례만 알려줘.
내가 직접 코드를 작성한 뒤 리뷰를 요청할게.
```

## 4. 확정된 기술 및 협업 결정 21개

### 4.1 협업 규칙

1. 브랜치는 `main`, `develop`을 사용한다.
2. AI·프론트엔드·백엔드 작업은 모두 `develop`에 모은다.
3. 직접 병합이 아니라 Pull Request 형식으로 리뷰 후 병합한다.
4. 커밋 컨벤션은 담당자가 대중적인 형식으로 정한 뒤 전체 팀에 공유한다.

> 커밋 컨벤션의 정확한 prefix와 문구는 아직 담당자가 문서화해야 한다.

### 4.2 문서·검색 구조

5. PostgreSQL에 `pgvector` 확장을 설치해 벡터 검색을 사용한다.
6. PostgreSQL 서버는 하나를 사용할 수 있지만 `app`, `ai` 영역을 분리한다.
7. 백엔드팀은 `app` 영역, AI팀은 `ai` 영역과 AI DB 테이블을 관리한다.
8. 개발 검증은 TXT로 시작한다.
9. MVP 지원 문서 형식은 DOCX다.
10. 이후 확장은 `PDF → CSV → XLSX → PPTX → 사내 위키 → HWP/HWPX → OCR` 순서로 진행한다.
11. 로컬 개발에서는 프로젝트 저장소 밖의 별도 문서 폴더를 사용한다.
12. 웹서비스 원본 문서는 S3에 저장한다.
13. PostgreSQL에는 문서명·권한·버전·S3 주소 등 메타데이터를 저장한다.
14. 문서 추가·수정 시 즉시 자동 재인덱싱한다.
15. 문서 삭제 시 즉시 검색에서 제외한다.
16. 인덱싱 실패 시 자동 재시도한다.
17. 이후 매일 새벽 S3·DB·AI 검색 데이터의 누락을 점검한다.

### 4.3 API·권한 계약

18. 백엔드는 AI 서버의 `POST /api/v1/chat/stream`으로 질문을 전송한다.
19. 요청 JSON은 `question`, `allowedScopes`, `conversationHistory`, `requestId`를 포함한다.
20. AI는 SSE로 `token`, `sources`, `complete`, `error` 이벤트를 백엔드에 보낸다.
21. 백엔드는 SSE 이벤트를 프론트엔드에 전달한다.
22. 문서 권한은 `PUBLIC`, `DEPT:<부서>`, `TEAM:<팀>` 범위로 관리한다.
23. 백엔드가 사용자의 허용 범위를 계산한다.
24. AI 서버가 검색 시 전달받은 허용 범위를 다시 적용한다.

> 위 목록은 세부 결정을 풀어 적어 24개 항목처럼 보이지만, 회의에서 관리한 결정 카테고리 기준으로는 총 21개다. `DB 관리 영역`, `지원 형식 단계`, `SSE 전달 흐름` 등의 세부 내용이 한 결정 안에 포함되어 있다.

### 4.4 평가 기준

- 평가 질문: 답이 있는 질문 40개 + 답이 없는 질문 10개
- 검색 합격: 50개 중 45개 이상에서 정답 문서가 Top 5에 포함
- 답변 합격: 50개 중 40개 이상에서 문서 근거에 맞게 답변
- 거절 합격: 답 없는 질문 10개 중 9개 이상에서 모른다고 답변
- 성능 합격: 질문 후 5초 안에 답변 시작, 20초 안에 전체 답변 완료

성능 기준은 실제 실행 장비에서 측정한 후 조정할 수 있다.

### 4.5 화면·완료 기준

- 출처 카드: 문서명, 관련 문장, 페이지 또는 문단, 원문 열기 표시
- 오류 분류: 잘못된 요청, 권한 없음, 관련 문서 없음, 검색 실패, 모델 실패, 시간 초과
- 오류 화면: 실패 이유, 다시 시도 버튼, 요청 ID 표시
- MVP 완료: 로그인 → 권한 확인 → 질문 → 검색 → 스트리밍 답변 → 출처 표시 → 대화 저장이 정상 동작하고 평가 기준 통과

## 6. 전체 아키텍처 방향

```text
프론트엔드
  → 백엔드(Spring)
      ├─ 사용자·조직·권한 확인
      ├─ 문서 메타데이터·대화 저장
      ├─ 원본 문서 S3 업로드
      └─ AI 서버에 질문·허용 범위 전달
            → AI 서버(FastAPI)
                ├─ 문서 추출·청킹
                ├─ bge-m3 임베딩
                ├─ pgvector 검색
                ├─ Qwen3 8B 답변
                └─ SSE 답변·출처·완료·오류

PostgreSQL
  ├─ app 영역: 백엔드 관리
  └─ ai 영역: AI팀 관리

S3
  └─ 원본 문서
```

## 7. 백엔드와 AI 데이터 책임

### 7.1 백엔드 관리 데이터

- 사용자·계정
- 부서·팀·직책
- 로그인·권한
- 문서 ID·문서명·작성자·공개 범위
- 원본 문서 S3 위치
- 문서 현재 버전
- 대화 기록
- 완성된 AI 답변과 참고 문서
- 온보딩 체크리스트와 완료 상태를 구현할 경우 해당 데이터

### 7.2 AI팀 관리 데이터

| 데이터 | 의미 |
|---|---|
| `document_id` | 백엔드 원본 문서와 연결하는 ID |
| `document_version` | 어떤 원본 버전으로 만들었는지 표시 |
| `chunk_id` | 잘라낸 문서 조각 ID |
| `chunk_text` | 검색 대상이 되는 실제 문장 |
| `chunk_order` | 원본 문서 안에서의 순서 |
| `embedding` | 문장의 의미를 변환한 검색용 벡터 |
| `source_location` | 페이지·문단·제목 등 원문 위치 |
| `index_status` | 대기·진행·완료·실패 상태 |
| `model_name` | 사용한 임베딩 모델과 버전 |
| `error_message` | 인덱싱 실패 이유 |

MVP 핵심 AI 데이터:

1. 원본 문서 ID
2. 문서 조각
3. 검색용 벡터
4. 원본 위치
5. 인덱싱 상태

### 7.3 분리 이유

- 백엔드 데이터는 없어지면 안 되는 서비스 정본이다.
- AI 데이터는 원본에서 다시 만들 수 있는 검색용 파생 데이터다.
- 모델·청킹 방식 변경 시 AI 데이터만 재생성할 수 있다.
- AI 작업 중 실수해도 사용자·권한·원본 문서를 보호한다.
- 각 팀의 코드·테이블·마이그레이션 책임이 명확해진다.
- 운영 복잡도를 줄이기 위해 PostgreSQL 서버 자체는 같이 쓸 수 있다.

## 8. 문서 인덱싱 파이프라인

```text
관리자 문서 업로드
→ 백엔드가 원본을 S3에 저장
→ 백엔드가 documentId·version·scope·S3 주소 저장
→ AI 서버에 인덱싱 작업 전달
→ AI 서버가 S3 원본 다운로드
→ 문서 텍스트 추출
→ 800자 청킹 + 120자 오버랩
→ bge-m3 임베딩 생성
→ pgvector에 문서 조각·벡터·원본 위치 저장
→ 인덱싱 완료 또는 실패 상태 반환
```

문서 변경:

```text
추가·수정
→ 새 버전 저장
→ 기존 검색 데이터 비활성화

→ 백엔드 문서 비활성화
→ AI 검색에서 즉시 제외
→ 관련 벡터 정리
```

## 9. 질문·답변 파이프라인

백엔드가 AI 서버에 보내는 요청 예시:

```json
{
  "question": "신입사원 식대는 어떻게 지급되나요?",
  "allowedScopes": ["PUBLIC", "DEPT:DEVELOPMENT", "TEAM:AI"],
  "conversationHistory": [],
  "requestId": "req-123"
}
```

흐름:

```text
사용자가 질문
→ 백엔드가 로그인·부서·팀 확인
→ 백엔드가 allowedScopes 계산
→ 백엔드가 AI 서버에 POST 요청
→ AI가 질문 임베딩 생성
→ 허용 범위 안에서 Top 5 검색
→ 검색 문서와 질문을 Qwen3 8B에 전달
→ AI가 token 이벤트로 답변 스트리밍
→ sources 이벤트로 출처 전송
→ complete 이벤트 전송
→ 백엔드가 완성 답변과 출처 저장
→ 오류 시 error 이벤트 전송
```

## 10. 패션 용어 설명 기능

프론트엔드에서 AI 챗봇이 패션 용어도 쉽게 설명해 주는 기능을 요구했다.

예상 용어:

- 원단·소재
- 색상·올리브그린
- 룩북
- 샘플
- 기획·디자인·생산·출시·다음 시즌

권장 방향:

- 패션 용어를 사전 또는 문서 형태로 관리한다.
- AI가 임의로 정의하기보다 등록된 설명을 우선 검색한다.
- 관련 문서가 있으면 출처를 표시한다.
- 일반 문서 질문과 용어 질문을 같은 챗봇에서 처리한다.
- 별도 위키·용어 사전 화면은 프론트·기획과 추가 조율한다.

미정:

- 용어 사전의 정본을 백엔드 DB로 둘지 문서로 둘지
- 관리자가 용어를 직접 등록·수정할지
- AI가 새로운 용어 후보를 추천할지

## 11. 팀 간 반드시 조율할 계약

### 백엔드 ↔ AI

- 문서 인덱싱 요청 payload
- 문서 ID·버전·S3 주소·권한 범위
- 문서 수정·삭제 이벤트
- 질문 요청 JSON
- SSE 이벤트 payload
- 오류 코드·타임아웃·재시도
- `app`, `ai` 스키마와 DB 계정 권한
- 완성 답변과 출처 저장 시점

### 프론트엔드 ↔ 백엔드·AI

- 스트리밍 답변 표시 방식
- 출처 카드 정보와 원문 열기
- 로딩·완료·오류·재시도 상태
- 패션 용어 설명 방식
- 대화 기록 화면
- 기본 모바일 반응형 범위

### 기획 ↔ 전체 팀

- 대상 회사를 단일 브랜드의 작은 의류 회사로 확정할지

- 온보딩 체크리스트를 MVP에 포함할지

### 인프라 ↔ 백엔드·AI

- S3 버킷과 접근 권한
- PostgreSQL·pgvector 설치
- Ollama·Qwen3 실행 환경

- DB·S3·내부 API 비밀값 관리
